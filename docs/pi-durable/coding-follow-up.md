更新日期：2026-11-06。功能基线：`feat/pi-durable-coding` 的 `f4f9f26`。

用户判断现有功能和插件契约已基本实现，要求先用源码和行为证据核实，不能直接将此判断作为验收结论。pi-durable 内核已有接入代码及历史验证。本次主任务是优化架构和依赖方式，减少升级上游 SDK 时需要维护的复制代码、内部修改及适配规则。[实施计划](durable-coding-agent-plan.md)保留历史账本，[需求对照](coding-acceptance.md)记录各功能的实现、证据版本和未验证范围。

## 目标与约束

MkAgent 主要基于 durable coding agent 运行：Coding 层承接 Pi coding agent 的能力和插件契约，已有 pi-durable 内核负责调度、存储及恢复，MkAgent 产品功能位于外层。当前功能是保留基线，先核实实际实现，不重新实施已有且满足契约的内核接入或 Coding 功能。

实现优先级为：先复用 pi-durable 内置能力；内置能力不足时，引用独立外部包补足；两者仍不能满足既定功能契约时，才做必要的薄适配或源码修改，并说明具体缺口。不能因 coding 与 durable 的调用协议不同就直接判定内置能力不可用，须先核实能否通过少量契约适配复用。允许按需使用 pi-agent-core，生产不能直接依赖完整 pi-coding-agent，也不能运行上游 Agent loop。

普通与 coding 模式保留工具、提示词、权限和资源发现策略。是否共用 AgentSession、内部任务类型及原生投影范围属于实现选择，不作为独立验收条件。源码数量和哈希追溯不能证明架构已经符合公开包优先的要求。

停止迭代的条件是：在保留既有功能和插件契约的前提下，维护成本已降到最低。逐项核对仍可消除的本地重复实现、内部修改和升级适配；只要还有可实施的降低方案，就继续处理。每项保留实现须有已核实的契约缺口，并说明公开包和薄适配为何不能替代。未核实或受阻的项保持开放，不能因完成一批改动、测试通过或本地提交而宣告达到目标。

## F1 架构与依赖清点

先按能力规格、需求对照和 MkAgent 保留清单，核对实际产品入口、实现调用链和已有行为证据。区分“已验证行为”“已有实现但缺少验证”“已确认缺失”和“环境受阻”，记录证据对应的提交及范围。缺少测试不直接等于功能缺失，历史通过也不等于当前改动已通过。

再按以下范围记录当前来源、公开包替代方式和本地差异：

| 范围 | 需要回答的问题 |
|---|---|
| 独立包 | pi-ai、pi-mcp、pi-codemode、pi-tui、pi-agent-core 和 pi-durable 的公开接口是否已充分复用 |
| Coding 会话、扩展、资源、工具及展示 | 哪些源码是必要例外，哪些只因完整闭包生成而被带入 |
| Agent 外观及执行桥接 | 哪些协议和状态操作可引用公开 core，哪些必须由 durable 负责 |
| 宿主策略 | 模型、压缩、资源信任、工具审批、UI 等是否可以通过公开接口放在外层 |
| 辅助层及旧入口 | 是否重复维护同源实现，哪些兼容入口可以转发到同一实现 |
| durable 补丁 | 哪些生产或旧 SDK 调用仍依赖，历史 checkpoint 是否阻止删除 |

完成条件：功能判断有实现和证据依据；每类保留或替代决定有具体调用、接口及契约依据，形成可执行的 F2/F3 改动项。无法核实的部分明确保留为待核实，不能归入“必要移植”。不能仅由“上游没有独立 coding SDK”推断全部源码都必须移植。

## F2 内置能力与公开包复用

先核对 pi-durable 已公开的 codemode、tool-search、tools、images、Harness、任务、存储及恢复能力。内置实现已有的算法和生命周期优先复用；宿主权限、动态目录或 coding 插件契约有差异时，先评估薄协议适配，不能把协议不同直接等同于必须重建实现。内置确有缺口后，再选用独立公开包。

已经完成的公开 core 协议类型和 streamProxy 引用继续保留。对 F1 找出的可替代项按上述顺序处理，保持已有入口和行为，避免另写一套等价实现。已有独立包依赖仍须核实是否可交由 durable 内置模块承接。

生产宿主已安装 durable 的 codemode、tool-search、tools、images，coding profile 通过 `hostToolToAgent` 和 `baseToolsOverride` 接收工具。本轮真实 codemode 沙箱检查先复现 Worker 回调的提交作用域丢失，再以捕获上下文的薄适配修正。内置工具的三项检查及组合回归通过，具体范围见[验证记录](coding-validation.md)。取消信号 helper 改为引用 `pi-ai/utils/abort`，只保留可选 signal 时的旧 Promise 身份。

继续核对后，等待 helper 也改为 `pi-ai/utils/sleep`，仅保留可选 signal 和既有取消错误的兼容。定时、取消监听和正常完成后的清理由公开包负责，普通定时错误仍原样传播。

SDK 搜索的分词、排序和 schema 文本已共用内置实现。由于正式公开入口缺少分数、可配置 `k1/b` 和纯元数据文本接口，仓内补丁增加三项兼容导出。原生工厂保留 namespace 字段、工具 exposure 过滤和会话启用回调；固定原版的 27 项排序用例及替换前后的差异对照通过。完整会话的声明更新、分支与恢复仍沿用既有证据范围，不由纯排序测试推定。

剩余重点是原生 codemode。真实 Harness 和沙箱对照确认 calls 类型、alias、输出预算、无 env 图片与 store 生命周期存在差异；原版内置也拒绝同名 discovery globals，当前补丁已允许覆盖。继续核对最小公开接点及外部适配，不以这些差异直接证明整套执行器必须保留。

输出切片已落地：SDK 共用内置 formatter，保留自己的 token 预算、文件写入和图片大小显示，执行文件净减少 191 行。96 个原版差异场景、公开类型及 25 份文件的 210 项组合回归通过。接下来将原生分支写入与内置执行结果放入同一事务，保留实时 calls 和发现元数据，继续替换执行核心。

journal 事务前置已完成：同一事务多次 flush 只准备新增操作，不重复导航或误判自身 replace；回滚后在新事务重新准备完整待提交阶段。宿主 commit 回调恢复调用方作用域，并在回调后再次 flush，把新增原生条目和宿主文档放入同一回执。9 项新增用例先红后绿，与原有测试合计 4 份文件、66 项、542 个断言通过，包含回执暂停期间追加条目。codemode store 接入和完整执行替换仍待实施，不把普通回调的外部副作用视为事务写入。

内置执行器的四个接点已交付到完整依赖补丁：原始 store 写入与执行结果共享事务，异步沙箱租约保留 deadline 和取消检查，输出策略支持 Native 预算和文件回调，discovery globals 可按名覆盖。6 项真实 Native journal fixture 覆盖分支读取、同值 set、删除不存在的 key、无 append、结果重用、脚本失败和写回拒绝。9 项公开入口测试验证其余策略，8 份文件共 95 项、676 个断言通过。干净离线 frozen install 的 16 个文件一致，独立消费者另通过 9 项、41 个断言。Native SDK 生产入口、实时 calls、插件通道、模型并发及完整恢复尚未接线验证，继续替换执行副本。

完成条件：确认可由 durable 内置模块满足的范围已优先复用；其余可由独立公开包满足的范围已改用包引用。没有因引用包启动上游 Agent loop，也没有引入被禁止的完整生产包。记录替代了哪些本地源码或转换，避免只换路径或包名而保留相同维护工作。

## F3 薄适配与必要例外

把可外移的宿主策略放到公开 API 的外部包装，减少对上游内部文件的修改。继续检查剩余辅助副本与原生移植实现是否重复；旧入口尽量转发，保留插件和 SDK 契约。

确需保留的源码及补丁分别记录用途、对应上游版本、缺少的公开接口、薄适配为何不足、升级时需要核对的范围。Pi v1.5.0 的 SDK 工厂固定创建 Agent 等限制只解释相关边界，不证明整个公开源码闭包都必要。

完成条件：已确认能减少的内部修改和重复实现已处理；剩余例外有依据；历史 checkpoint、存量会话及旧 SDK 兼容保持可用。现有生成及哈希机制继续用于溯源，不作为维护成本已降低的替代证据。

## F6 架构与升级验收

同步本清单、实施计划、能力规格、需求对照、架构和验证记录。最终按以下问题验收：

1. durable 内置能力是否已优先复用，缺失能力是否再优先引用独立外部包。
2. 公开接口不足时，适配是否尽量薄并位于外层。
3. 必要源码或补丁的保留理由是否具体，升级核对范围是否清楚。
4. 架构调整后，现有产品功能和插件行为是否通过对应验证。
5. 未完成的检查及来源访问阻塞是否如实保留。

升级目标是尽量只需更新包版本并运行兼容检查；当前仍有必要移植和补丁时，明确剩余适配工作，不能承诺已经达到仅改版本号。Windows、正式签名公证安装及系统协议只核查本次改动影响。

先完成文档修正及查漏补缺，再按 F1 至 F6 落实。每项开始时对照用户要求、既定契约和通过条件，结束时对照实际 diff 与验证结果。发现无依据的新要求、功能裁剪或错误结论，立即停止相关改动，修正任务及文档，再恢复执行。受阻检查没有通过前，不声明整体任务或全部验收完成；已完成且验证的范围仍可按授权本地提交。
