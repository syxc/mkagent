# Durable coding agent 架构优化跟进

更新日期：2026-11-06。功能基线：`feat/pi-durable-coding` 的 `f4f9f26`。

用户判断现有功能和插件契约已基本实现，要求先用源码和行为证据核实，不能直接将此判断作为验收结论。pi-durable 内核已有接入代码及历史验证。本次主任务是优化架构和依赖方式，减少升级上游 SDK 时需要维护的复制代码、内部修改及适配规则。[实施计划](durable-coding-agent-plan.md)保留历史账本，[需求对照](coding-acceptance.md)记录各功能的实现、证据版本和未验证范围。

## 目标与约束

MkAgent 主要基于 durable coding agent 运行：Coding 层承接 Pi coding agent 的能力和插件契约，已有 pi-durable 内核负责调度、存储及恢复，MkAgent 产品功能位于外层。当前功能是保留基线，先核实实际实现，不重新实施已有且满足契约的内核接入或 Coding 功能。

实现优先级为：直接引用可用的独立公开包；公开接口不足时采用薄的外部适配；只有两者均不能满足既定契约时，才保留必要源码移植，并说明原因。允许按需使用 pi-agent-core，生产不能直接依赖完整 pi-coding-agent，也不能运行上游 Agent loop。

普通与 coding 模式保留工具、提示词、权限和资源发现策略。是否共用 AgentSession、内部任务类型及原生投影范围属于实现选择，不作为独立验收条件。源码数量和哈希追溯不能证明架构已经符合公开包优先的要求。

## F1 架构与依赖清点

先按能力规格、需求对照和 MkAgent 保留清单，核对实际产品入口、实现调用链和已有行为证据。区分“已验证行为”“已有实现但缺少验证”“已确认缺失”和“环境受阻”，记录证据对应的提交及范围。缺少测试不直接等于功能缺失，历史通过也不等于当前改动已通过。

再按以下范围记录当前来源、公开包替代方式和本地差异：

| 范围 | 需要回答的问题 |
|---|---|
| 独立包 | pi-ai、pi-mcp、pi-codemode、pi-tui、pi-agent-core 和 pi-durable 的公开接口是否已充分复用 |
| Coding 会话、扩展、资源、工具及展示 | 哪些源码是必要例外，哪些只因完整闭包生成而被带入 |
| Agent 外观及执行桥接 | 哪些协议和状态操作可引用公开 core，哪些必须由 durable 负责 |
| 宿主策略 | 模型、压缩、资源信任、工具审批、UI 等是否可以通过公开接口放在外层 |
| 辅助层及旧入口 | 是否重复维护同源实现，哪些兼容入口可以转发到同一实现 |
| durable 补丁 | 哪些生产或旧 SDK 调用仍依赖，历史 checkpoint 是否阻止删除 |

完成条件：功能判断有实现和证据依据；每类保留或替代决定有具体调用、接口及契约依据，形成可执行的 F2/F3 改动项。无法核实的部分明确保留为待核实，不能归入“必要移植”。不能仅由“上游没有独立 coding SDK”推断全部源码都必须移植。

## F2 公开包复用

已经完成的公开 core 协议类型和 streamProxy 引用、现有 Pi 独立包依赖继续保留。对 F1 找出的可替代项优先直接引用包，保持已有入口和行为，避免另写一套等价实现。

完成条件：所有确认可由现有公开包满足的范围已改用包引用；没有因引用包启动上游 Agent loop，也没有引入被禁止的完整生产包。记录替代了哪些本地源码或转换，避免只换路径或包名而保留相同维护工作。

## F3 薄适配与必要例外

把可外移的宿主策略放到公开 API 的外部包装，减少对上游内部文件的修改。继续检查剩余辅助副本与原生移植实现是否重复；旧入口尽量转发，保留插件和 SDK 契约。

确需保留的源码及补丁分别记录用途、对应上游版本、缺少的公开接口、薄适配为何不足、升级时需要核对的范围。Pi v1.5.0 的 SDK 工厂固定创建 Agent 等限制只解释相关边界，不证明整个公开源码闭包都必要。

完成条件：已确认能减少的内部修改和重复实现已处理；剩余例外有依据；历史 checkpoint、存量会话及旧 SDK 兼容保持可用。现有生成及哈希机制继续用于溯源，不作为维护成本已降低的替代证据。

## F4 功能与插件回归

功能和插件契约作为架构调整的保留基线。按受影响范围选择已有用例：

| 改动范围 | 验证重点 |
|---|---|
| Agent 协议、请求及工具桥接 | 固定原版 17 场景、工具审批、事件顺序、取消、结构化结果 |
| 插件加载、资源及包管理 | 原样插件、两个 loader、Bun 元数据、reload、项目信任和显式安装 |
| 会话与持久化适配 | new/fork/switch/tree、原始输入身份、严格回执、SQLite/JSONL 冷恢复 |
| 模型及 MCP 适配 | 注册、动态目录、授权、撤销、reload/reopen，使用本地替身 |
| UI 或展示适配 | 原版 RPC 契约及受影响的 SDK TUI 行为，记录原生宿主边界 |
| 产品装配及公开入口 | 普通与 coding 模式原有行为、独立包消费者、声明及 worker 构建 |

最终完成相关产品与仓库回归、validate:ci、lint 和完整变更的独立复核。新增测试须针对实际变更、发现的缺陷或确认的验证缺口，不重做已有功能。历史未覆盖的交互或平台结果如实保留，不自动扩大本阶段范围。

执行检查前核对它是否直接或间接触及 F5 的受限源码。受影响的检查同样保留阻塞；不能为获得通过结果而越过访问边界，也不能把缩小范围的检查称为完整通过。

`f4f9f26` 既有 84 份文件、971 项测试及产品定向证据，该轮合跑超时后分批补齐，没有重跑全仓测试。后续证据须注明适用提交和实际命令结果，不能沿用旧提交的全仓结果声称最新实现全量通过。

## F5 来源检查边界

辅助层生成检查已有通过证据。完整运行时生成检查和全量 Craft 审计会读取受限凭据源码，现有边界下不得执行或重试。不得直接或间接读取本地或上游的 `runtime-credentials.ts`。

局部哈希核对不能算完整复现。这是来源验证阻塞，不是 Coding 功能缺失。保留已有证据、未验证范围和阻塞，符合访问边界的完整验证结果出现前不关闭本项。

## F6 架构与升级验收

同步本清单、实施计划、能力规格、需求对照、架构和验证记录。最终按以下问题验收：

1. 可以引用包的实现是否已优先引用包。
2. 公开接口不足时，适配是否尽量薄并位于外层。
3. 必要源码或补丁的保留理由是否具体，升级核对范围是否清楚。
4. 架构调整后，现有产品功能和插件行为是否通过对应验证。
5. 未完成的检查及来源访问阻塞是否如实保留。

升级目标是尽量只需更新包版本并运行兼容检查；当前仍有必要移植和补丁时，明确剩余适配工作，不能承诺已经达到仅改版本号。Windows、正式签名公证安装及系统协议只核查本次改动影响。

先完成文档修正及查漏补缺，再按 F1 至 F6 落实。每项开始时对照用户要求、既定契约和通过条件，结束时对照实际 diff 与验证结果。发现无依据的新要求、功能裁剪或错误结论，立即停止相关改动，修正任务及文档，再恢复执行。受阻检查没有通过前，不声明整体任务或全部验收完成；已完成且验证的范围仍可按授权本地提交。
